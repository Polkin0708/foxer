# Архитектура

Поведение продукта задают [требования](requirements.md), торговые правила —
локальный `strategy/fvg-bot-rules.json`. [План](development-plan.md)
отделяет выполненное и проверенное от оставшихся работ. Ниже описано целевое
устройство по текущему JSON, а не утверждение о готовности всех частей кода.

## Поток обработки

Предыдущие свечи и текущие котировки → расчёт по каждой паре → планы и сигналы → Telegram.
Ответ на сигнал текстом или скриншотом → сохранение → OpenAI → проверка и запись JSON
→ пересчёт ожидающих планов → пояснение в Telegram.

Серверный бот — один Rust-процесс. Координатор последовательно меняет состояние;
рабочие потоки получают котировки, Telegram updates, ответы OpenAI и доставляют
сообщения. Медленный HTTP-запрос не останавливает обработку котировок.
OpenAI используется для комментариев, а не для расчёта каждого сигнала.

Разработка, тесты и сборка выполняются в Docker; на Ubuntu 26.04.1 LTS запускается
готовый Linux x86_64-бинарник под systemd. Версии заданы в Dockerfile и Cargo.lock;
зависимости — в bot/Cargo.toml. SQLite хранит состояние, Telegram работает через long polling.

## Загрузка стратегии

При запуске читается локальный рабочий JSON, исключённый из Git.
`example.json`, встроенные параметры и содержимое SQLite не подменяют файл.
Тесты читают рабочий JSON; после клонирования, перед запуском тестов и приложения,
он создаётся вручную из `example.json` по инструкции README. Контракт проверяет обязательные
и неизвестные поля, типы, повторные ключи, ID правил, диапазоны, перечисления и ссылки.
Числа должны быть конечными; объём свечей — не меньше минимума, RR — положительным
и согласованным с потолками. Инструменты уникальны, шаг цены положительный.

Условия JSON сопоставлены типизированным блокам Rust по ID, а не позиции в массиве.
Текст формул и определений не исполняется как код. Параметры читаются из JSON;
неподдерживаемая политика отклоняется явно. Ограничения текущей реализации
перечислены в плане и не меняют смысл стратегии.

| Разделы JSON | Ответственность |
|---|---|
| `instruments`, `candles`, `context`, `policies.trade_window` | Инструменты, свечи, достаточность данных, доступное время торговли |
| `policies.zones`, `policies.fractals`, `parameters` | ATR, зоны, фракталы, направление и параметры расчёта |
| `policies.plans` | Планы W/D/H4, подтверждение, вход, сроки, сопровождение |
| `policies.targets`, `policies.execution` | Цели, цена входа, стороны котировки, отмены |
| `policies.positions` | Независимость планов, защита от дублей, применение новых правил |
| `policies.modules` | Признак отключённого модуля боковиков |

`check-config [путь]` проверяет файл без сети и изменений: код 0 — успех,
1 — ошибка чтения/конфигурации, 2 — аргументы. Без пути используется
`strategy/fvg-bot-rules.json` относительно текущего каталога.
`describe-config [путь]` выводит JSON Pointer полей, значения без пояснений,
ограничения параметров, допустимые политики, пути comment и разрешение Telegram-правок.
Карта не подтверждает выполнение торговых правил; готовность определяется тестами
и приёмкой в плане. Диагностика не печатает значения ошибочных полей и секреты.

## Данные каждой пары

Координатор хранит отдельные движок, агрегатор и признак доступности потока для
каждого символа из `instruments`. Свечи, планы, сигналы и события имеют символ
в ключе; шаг цены берётся из `instruments[].price_tick`, масштаб —
`instrument_price_tick_scale`. Единица цены — валюта котировки за единицу базовой
валюты, а не USD за EUR для всех инструментов. Цены представлены целыми числами;
округление входа не должно ухудшать требуемый RR, отступ стопа округляется наружу.

HistData импортируется из подготовленных M1 с отчётом качества. Проверяются источник,
исходная временная зона UTC−5, UTC-время, длительность минуты, OHLC, Bid/Ask,
размеры и SHA-256 файлов. Исходные архивы не меняются. Неоднозначные интервалы
исключаются при подготовке и отражаются в отчётах. Импорт атомарен; повтор
одинаковых данных идемпотентен, конфликт источника/символа/минуты откатывает импорт.

Biquote предоставляет REST-снимок `/api/{symbol}` и SignalR-поток `/hubs/tick`.
Подписка соответствует списку инструментов. Проверяются символ, источник,
положительные Bid ≤ Ask и UTC timestamp. Повтор одинакового события не создаёт
повторного действия, обратное время отклоняется. Источники не склеиваются незаметно;
пропуски не заполняются. REST при закрытом рынке не доказывает работу живого потока.

## Свечи и расчёт текущей ситуации

Для импортированных минут и потока используется одна сетка из `candles`:
America/New_York с DST, D1 в 17:00, неделя с воскресенья 17:00, H4 в 01/05/09/13/17/21.
При повторяющемся осеннем 01:00 границей служит первое вхождение; длина
интервала в UTC меняется вместе с DST. RR поддерживает до девяти десятичных
знаков и значения до 1000000; расчёт использует целочисленные дроби без усечения.

Время хранится в UTC. Интервалы полуоткрытые: котировка на границе относится
к следующей свече. На общей границе обработка идёт W → D → H4.

Из предыдущих закрытых свечей рассчитываются зоны, фракталы и направление.
Количество и минимумы задаёт `context`. Эта загрузка не создаёт прошлые планы и сигналы. В коде операция называется `seed`;
это внутренняя часть загрузки данных, отдельного режима продукта нет.
Повтор одинакового закрытого бара не меняет результат; другая версия уже
обработанного бара и обратное время отклоняются.

Агрегатор сохраняет незакрытые Bid-бары и последнюю котировку. Пустые интервалы
не создаются. Первый неполный бар, бары после разрыва потока и незакрытые бары
после перезапуска не выдаются за полностью наблюдавшиеся. Новые сигналы требуют
свежих котировок и достаточных данных; сопровождение выданных сигналов продолжается
по наблюдаемым ценам. Движение цены за пропуск не восстанавливается предположением.

## Расчёты и состояния

ATR, образование FVG/гэпов, реакции, инверсии, фракталы и направление вычисляются
по `policies.zones` и `policies.fractals`. ATR зоны выбирается через
`parameters.atr_reference_zone`, стопа — `policies.atr.stop_reference`. Гэп отличается способом образования и далее проходит
те же правила зоны. Происхождение зоны сохраняется для объяснения сигнала.

План хранит инструмент, ID правила, время, направление, POI и её таймфрейм.
Состояния определены типами движка: `wait_confirm`, `wait_entry`, `setup`, `active`, `done`.
У четырёх дневных правил correction/continuation POI дневная; у `W_point_A` недельная.
Повтор правила для той же ситуации не создаёт дубля, независимые планы не теряются.
Смена недельного направления обрабатывает каждый план согласно `policies.plans.weekly_rules`;
активный сигнал продолжает сопровождаться отдельно до результата.

Подтверждение и вход проверяются по `policies.plans` и `parameters`. Возраст зон, включение IFVG,
допустимый диапазон лимитной цены и сроки ожидания берутся из JSON. Отключённые
модули не участвуют в расчёте. Точные условия не дублируются вторым алгоритмом
в документации. Структурная цель и ограниченный потолком тейк сохраняются отдельно.

Политика `policies.execution.limit_entry=solve_rr_min_keep_stop_target` реализует формулу:
`entry = (target + rr_min * stop) / (1 + rr_min)`. Минимум и потолки читаются
из параметров; фиксированных политик 2R/10R в коде быть не должно. Для коррекции
используется `rr_max_correction`, для trend/continuation — `rr_max_trend`.
Покупка входит по Ask и выходит по Bid; продажа — наоборот.

После закрытия подтверждающей H4 используется первая доступная котировка.
Отмена ожидающего входа проверяется до исполнения: стоп/цель по стороне выхода,
условие пробоя инвертированной зоны — по закрытию H4 и запасу из JSON.
Закрытые бары и истечение срока обрабатываются до входа по котировке.
Отмена терминальна; последующее касание входа не активирует отменённый сигнал.
Стоп/тейк отслеживаются по котировкам, без ожидания следующей H4 и без
предполагаемого порядка движения внутри свечи.

## Сохранение и восстановление

SQLite содержит котировки, отчёты импорта, состояние расчёта, планы, сигналы,
результаты, комментарии, авторов, привязки сообщений и задания. Конфигурация
хранится только в JSON; снимок содержит хеш правил и состояния по символам.
Изображения сохраняются рядом с БД в `attachments` с идентификацией по SHA-256.

В одной транзакции сохраняются входное событие, изменения состояния и очередь
исходящих сообщений (outbox). Только после успешной записи меняется состояние
в памяти. Повтор ID и содержимого события не применяет его заново; конфликт
содержимого отклоняется. Подтверждение доставки и привязка Telegram-сообщения
к сигналу также сохраняются атомарно. Недоставленные сообщения остаются после сбоя.
Потерянный ответ Telegram может дать дубль доставки; exactly-once не обещается.

Миграции изменяют существующую БД транзакционно с сохранением данных. Версия
схемы проверяется; чужая БД и неизвестная будущая версия отклоняются.
Миграция на новую сетку свечей сохраняет опубликованные сигналы, их уровни и зоны,
результаты, комментарии и привязки; неопубликованные ожидания удаляются, расчёт
зон и направления восстанавливается из исходных минут. Повтор после сбоя безопасен.
Устаревшие задания изменения опубликованных уровней больше не доставляются
и не применяются. Это переход со старой реализации, а не постоянный режим торговли.

## Комментарии и изменение JSON

Telegram принимает ответы из настроенной группы на известный сигнал или уточнение.
Сохраняются update_id, message_id, chat_id, author_id, текст/подпись и изображения.
Все участники равноправны. Offset увеличивается после устойчивого сохранения update.
Фото выбирается в максимальном разрешении; изображение-файл проверяется по MIME
и сигнатуре PNG/JPEG/WebP/GIF. Ошибка загрузки не заменяется пустым изображением.

FIFO-очередь обрабатывает каждый ответ как новое дополнение на актуальных правилах.
OpenAI Responses API получает модель из сервисных настроек, `store=false`, лимит
ответа, нужные правила, связанный сигнал, текущий комментарий и изображения.
Для уточнения добавляется относящаяся к нему ветка, а не весь чат. Ответ имеет
строгую схему `apply/clarify/no_change`, пояснение и изменения действующих скалярных параметров и строковых comment
по разрешённым JSON Pointer из каталога контракта. Новые алгоритмы и произвольные пути не применяются.
Неоднозначный комментарий вызывает уточнение без изменения правил.

Кандидат проверяется целиком. Сохраняются ID операции и хеши полного документа до/после без копии
правил; расчётный хеш исключает comment и messages; файл записывается через временный файл и атомарный rename, затем фиксируются
состояние и сообщения. После сбоя операция сверяется с JSON и завершается без
повторного применения правки. Ошибка записи не меняет правила в памяти.

После изменения пересчитываются `wait_confirm`/`wait_entry` с сохранением их
идентичности и времени жизни. `setup`/`active` сохраняют вход, стоп, структурную
цель и тейк согласно `position_rules.rule_update`; завершённые результаты неизменны.
В чат отправляются пояснение изменения и новые условия ожидающих планов.
Доставка пояснения не переключает уровни опубликованного сигнала.

## Сбои и внешние вызовы

| Сбой | Действие |
|---|---|
| Нет котировок | Уведомить группу, приостановить новые сигналы; не приписывать результаты пропущенному периоду. |
| Нет OpenAI | Уведомить, продолжать сигналы по JSON, сохранять комментарии и автоматически продолжить очередь после восстановления. |
| Нет Telegram | Сохранить исходящие сообщения до восстановления. |
| Ошибка записи состояния | Завершить процесс; systemd перезапустит его с сохранённым состоянием. |
| Невалидная правка | Сохранить действующий JSON, дать пояснение, не повторять платный запрос бесконечно. |

Сетевые запросы имеют connect/request timeout, предел размера ответа и ограниченные
повторы с задержкой. Ошибки доступа, временные сбои и невалидные ответы различаются;
уведомление создаётся один раз на инцидент. HTTP-транспорт подменяется в тестах.
Токены, Authorization, тела ответов и URL Telegram с токеном не попадают в диагностику.
API-модель не получает доступ к SSH или shell. Расход токенов сохраняется при наличии usage.
Большие пояснения разбиваются до 3500 UTF-16 единиц с сохранением порядка и привязки.

## Запуск, диагностика и поставка

Сервисные настройки читаются из отдельного `.env`: Telegram-токен/группа,
OpenAI-ключ/модель, пути JSON/БД, лимит ответа и контроль свежести котировок.
Shell-интерполяция запрещена; неизвестные и повторные ключи — ошибка.
Старый `PRICE_TICK` допускается для совместимости, но расчёты используют JSON.
Секреты не входят в стратегию, тестовые фикстуры и обычный release-архив.

| Команда | Назначение |
|---|---|
| `run <env-file>` | Запуск координатора и внешних адаптеров |
| `check-service <env-file>` | Проверка настроек и стратегии без сети |
| `import-histdata <db> <root>` | Проверенный импорт подготовленных минут |
| `inspect-db <db> <as-of-UTC>` | Просмотр сохранённых минут и закрытых свечей |
| `smoke-test <db> <strategy>` | Автономный искусственный сценарий на новой тестовой БД |
| `probe <env-file>` | Отдельная read-only проверка Telegram getMe/getChat и снимка котировок |

Живые проверки запускаются отдельно по задаче. Smoke-test не использует рабочую БД.

Служебные сообщения и логи заданы в требованиях. Лог H4 не создаётся для повторного,
незакрытого или неполного бара и при загрузке предыдущих свечей. Смена недельного
состояния уведомляет по `weekly_rules`; повтор события не дублирует уведомление.

Release собирается под linux/amd64, запускается локально в Docker и передаётся
пользователю для ручной установки. systemd обеспечивает автозапуск, перезапуск,
journald и отдельного пользователя. Обычный архив содержит бинарник без рабочих
данных и ключей. Комплект обновления `deploy` содержит только бинарник, новый JSON, инструкцию
и контрольные суммы. БД, секреты и unit не поставляются. После остановки службы
устанавливаются бинарник и JSON; prepare-state пересчитывает существующую
серверную БД на месте. Резервная копия по указанию пользователя не создаётся.
Каталог deploy целиком исключён из публичного репозитория. Файлы доставляются
в выбранный владельцем сервера каталог; пути запуска берутся из существующего
unit, пути БД и JSON — из файла настроек относительно рабочего каталога службы.
Пути конкретной серверной установки в публичной документации не указываются.
Обновление приложения не подменяет рабочую БД локальным снимком и не меняет ключи. Установка и проверка
на сервере отмечаются отдельно от локальной сборки.

## Общая библиотека и локальный бэктест

Workspace: forex-core (контракт, календарь, агрегатор, движок), forex-bot
(серверные адаптеры/SQLite), forex-backtest (архивы, журнал, статистика).
Общий обработчик принимает тик, возвращает закрытые бары и изменения сигналов
с основанием; порядок W/D/H4 → отмены/сроки → котировка одинаков для обеих программ.
Сериализованные состояния сохраняют прежнюю форму. Границы свечей кешируются.
Подготовленные CSV M1 читаются до явного as-of без SQLite/now(); текущие свечи
восстанавливаются с признаками полноты. Тики ZIP читаются потоково, проверяются
SHA-256, UTC−5, порядок, Bid/Ask и исключения quality-report. При равном времени
между парами порядок instruments, внутри пары порядок файла. Журнал хранит миллисекунды.
Известный пропуск вызывает disconnected агрегатора; отсутствие тиков само по себе
не доказывает сбой. Обе программы используют одну стратегию, новый слой бэктеста
только записывает исполнения и R. Rust готовит статистику и примеры; Python
Matplotlib/ReportLab рисует и верстает. Серверная сборка исключает Python и backtest.
Архивы и входные файлы read-only, результат в отдельном каталоге; исходный JSON
снимается один раз. seed примеров фиксирован. Установка и изменения на сервере исключены.

Локальная команда поддерживает --no-pdf и --report-only RESULT_DIR. Результаты
записываются в новый каталог: strategy.json, results.json (включая данные графиков),
events.jsonl, trades.csv, report.pdf. PDF после сбоя можно собрать без повторного
расчёта. Шаги данных не используют рабочую SQLite. Docker монтирует только выбранные
каталоги HistData и стратегию read-only; результат writable, сеть отключена.
Python и системные зависимости отчёта закреплены версиями; Python/Rust-образы — digest.

### Визуальное оформление PDF

Утверждённый образец — локальный отчёт `reports/backtests/october-2026/report.pdf`
после обновления оформления 10.11.2026: шесть страниц, включая четыре примера.
Производный PDF не требуется хранить в репозитории; воспроизводимый шаблон —
[backtest/report/render.py](../../backtest/report/render.py). Этот раздел фиксирует
его визуальный стандарт для последующих изменений. Оформление не пересчитывает
сделки, статистику или выбор примеров.

**Страница и типографика.** A4, книжная ориентация, белый фон. Боковые поля
48 pt, верхнее 62 pt, нижнее 49 pt. Шрифт DejaVu Sans с кириллицей встроен в PDF;
для заголовков и значений используется Bold. Главный заголовок — 29/35 pt
(кегль/интерлиньяж), заголовки разделов — 15/20, основной текст — 8,5/12,
примечания — 7/10, таблицы — 7,5/10. Сохраняются свободные поля и ясная иерархия,
без отдельной декоративной обложки.

**Палитра.** Цвета одинаковы в вёрстке и графиках:

| Назначение | Цвет |
| --- | --- |
| Шапка, заголовки, основной текст, уровень входа | `#142D46` |
| Бирюзовый акцент, растущие свечи, тейк | `#087F8C` |
| Убыток, падающие свечи, стоп | `#C4474B` |
| Вторичные подписи | `#5B6D7C` |
| Фон карточек | `#EDF3F7` |
| Чередующаяся строка таблицы | `#F7F9FB` |
| Фон предупреждения / левая полоса | `#FFF1E8` / `#D5894B` |

**Общие элементы.** Верхняя тёмно-синяя полоса высотой 43 pt содержит белые
`FOREX / RESEARCH` слева и `BACKTEST / версия` справа. Внизу — тонкая линия,
пометка локального расчёта, первые 12 символов хеша правил и номер страницы
двумя цифрами. Карточки стоят по три в ряд, расстояние 9 pt, высота фона 64 pt,
радиус углов 7 pt. Внутри: небольшая подпись 7,5 pt, короткий цветной штрих
и крупное значение Bold 23 pt. Таблицы имеют тёмно-синюю шапку с белыми жирными
подписями, тонкую бирюзовую линию под ней и чередующиеся белые/светлые строки;
без тяжёлой сетки. Шапка повторяется при переносе. Пустые таблицы не рисуются.
Предупреждения выделяются светлой персиковой плашкой с левой полосой 3 pt.

**Композиция отчёта.**

1. Сводка «Стратегия в цифрах»: период UTC и пары; два ряда карточек
   (результат закрытых, просадка закрытых, число сделок; доля прибыльных,
   средняя сделка, profit factor); кривая R и просадка; краткая оговорка
   методики; таблица результатов по парам.
2. С новой страницы — «Детали и качество данных»: месяцы, длительность,
   открытые/ожидающие/отменённые сигналы, покрытие котировок, плашка пропусков,
   объём начальных свечей, происхождение и хеш правил, методика исполнения.
3. Каждый пример начинается с новой страницы: номер разбора, крупные пара
   и направление, три карточки (реализованный R, вход, исходный стоп), время
   и правило, предупреждение при наличии пропусков. Затем два крупных графика
   друг под другом: POI на D или W и вход на H4. Внизу — пояснение о снимке
   основания и последующих свечах.

**Графики.** Белый фон, тонкая ненавязчивая сетка, без верхней и правой рамок,
подписи слева. Кривая закрытого R ступенчатая; цвет красный при отрицательном
итоге, иначе бирюзовый. Просадка ниже неё, с полупрозрачной красной заливкой.
Свечи бирюзовые/красные, зона решения — бирюзовая заливка с прозрачностью 0,13.
Вход, стоп и тейк показаны пунктиром и подписаны в легенде вместе с ценами.
Время входа/выхода отмечается вертикальными линиями только внутри видимого
диапазона. На каждом свечном графике указаны таймфрейм, Bid и UTC;
для W даты имеют формат месяц/год, для D/H4 — день/месяц.
Изображения Matplotlib сохраняются с 180 dpi и масштабируются пропорционально:
блок кривой вписывается в высоту 240 pt, каждый свечной график — 265 pt.

Количество страниц адаптируется к объёму таблиц и примеров; шесть страниц
образца не являются лимитом. При изменении шаблона проверяются извлечённый
русский текст и все отрендеренные страницы: читаемость, переносы, отсутствие
обрезанных подписей и наложений. Проверки пустого отчёта и повторяемости PDF
сохраняются; красивое оформление не должно скрывать отрицательные результаты
или ограничения данных.

### Ошибка определения пары сигнала

`signal_text` читает символ из префикса ID (`SYMBOL:...`) и проверяет его
существующим валидатором инструментов. При отсутствующем или некорректном
префиксе возвращается ошибка «Не удалось определить пару сигнала». Вызывающий
Runtime передаёт ошибку выше до записи события и исходящего сообщения.
Подстановка EURUSD удалена; формат текущих корректных ID и снимков не меняется.

## Контракт стратегии v2 (согласовано)

Рабочий JSON и example.json переводятся непосредственно на schema_version=2.
Конвертера, старого загрузчика и чтения чисел из текста нет. Корневые разделы:
comment, schema_version, instrument_price_tick_scale, instruments, candles,
context, parameters, policies, messages. Фактические торговые значения сохраняются.
parameters содержит только действующие настройки в объектах value/comment.
policies явно задаёт реализованные алгоритмы и ограничения; неподдерживаемые
значения отклоняются. Опциональный строковый comment разрешён у объектов,
но не участвует в расчётах. Сообщения хранятся отдельно от условий.

Пять ранее текстовых настроек становятся положительными целыми параметрами:
stop_fallback_h4_bars=10, confirmation_inversion_h4_bars=30,
weekly_fractal_sweep_lookback_bars=60, target_fractal_lookback_d_bars=80,
target_fractal_lookback_w_bars=60. Это значения текущего файла, не константы движка.
weak_bars удаляется: модуль слабости отключён. Отметка снятого дневного фрактала
за 30 баров не реализована и не превращается в действующую настройку.

OpenAI получает документ с пояснениями и каталог разрешённых путей. Может менять
действующие скалярные параметры и comment, но не структуры, инструменты или
фиксированные политики. Неподдерживаемая просьба требует уточнения. Полный кандидат
проверяется перед атомарной записью; незатронутые пояснения сохраняются.
Хеш документа включает comment/messages и используется для восстановления записи.
Расчётный хеш исключает comment/messages: их изменение не пересчитывает планы.
Сохраняются FIFO, защита опубликованных уровней и идемпотентность после сбоя.

Старый снимок SQLite без незавершённой операции обновляет формат хешей и один раз
пересчитывает ожидающие планы. Идентификаторы, сроки, опубликованные уровни,
история, очередь и привязки сохраняются. Незавершённая операция старого формата
останавливает загрузку с диагностикой без изменения снимка. Рабочая база не
мигрируется при разработке: приёмка выполняется на копии.

## Цели Docker-сборки

Единый Dockerfile предоставляет dev, release и backtest. Общая Rust-база
закреплена digest; общий слой исходников используется двумя независимыми
сборками forex-bot и forex-backtest. dev содержит rustfmt/Clippy, release
экспортирует только forex-bot, backtest содержит Python и PDF-зависимости.
Compose явно выбирает dev для rust и backtest для backtest. Allowlist
.dockerignore сохраняет исключение секретов, данных и рабочего JSON.

Публичный data/example.sql содержит только DDL текущей SQLite-схемы и
application_id/user_version. Он создаёт пустую базу v3 без пользовательских
записей и не выполняет миграции существующих данных.
