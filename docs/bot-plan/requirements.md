# Требования к Telegram-боту Forex

Единственный источник торговых правил — локальный `strategy/fvg-bot-rules.json`,
торговая редакция `agreed-v4`, формат v2. При расхождении торгового описания с JSON исправляется
документация. Рабочий файл исключён из Git; начальная конфигурация — [example.json](../../example.json).
Этот документ задаёт продукт и поясняет действующие правила; [архитектура](architecture.md)
описывает устройство, [план](development-plan.md) — работы и результаты проверок.
Наличие требования не означает, что оно уже реализовано и проверено.

## Продукт

| ID | Требование | Основание |
|---|---|---|
| R1 | Бот написан на Rust под Ubuntu 26.04.1 LTS. Разработка и сборка выполняются в Docker; на сервере готовый бинарник запускается под systemd. | Прямое указание пользователя при запросе плана и подтверждённый выбор окружения разработки и запуска. |
| R2 | Стратегия задаётся рабочим strategy/fvg-bot-rules.json с уточнениями пользователя. Поддерживаемые правила меняются через JSON без переписывания бота. | Уточнение «Я дам тебе готовый json с правилами» и принятый подход конфигурации. |
| R3 | Пользователь создаёт Telegram-группу, добавляет бота; бот присылает туда торговые сигналы. Формат: валютная пара, покупка или продажа, время, вход, стоп, цель, RR и краткое объяснение по правилам JSON. | Исходный порядок работы, пункты 1–3; формат сигнала подтверждён пользователем. |
| R4 | Участники настроенной Telegram-группы комментируют сигнал текстом и скриншотами графиков ответом на сообщение бота с сигналом в Telegram. Все участники группы имеют равные права изменять правила через комментарии. Текст и изображения сохраняются с привязкой к этому сигналу и используются при API-разборе с первого выпуска. | Исходный порядок работы, пункты 4–5; уточнение «Нужны сразу скриншоты»; подтверждены отправка ответом на сигнал и равные права обоих авторов. |
| R5 | Комментарий запускает обработку через OpenAI API; изменения правил применяются сразу по результату обработки, без отдельного подтверждения. Каждый ответ любого участника группы считается новым дополнением и обрабатывается последовательно, в порядке поступления, с учётом уже применённых изменений. Однозначное новое дополнение может изменить ранее установленное правило без согласования между авторами. При неоднозначности самого комментария бот уточняет его смысл в чате и не применяет неоднозначное изменение. После изменения JSON бот кратко сообщает в чат, что изменил и по какому комментарию; пересчитывает планы wait_confirm/wait_entry по новым правилам и сообщает новые условия в чат. | Уточнения «применять изменения сразу после комментария», заменяющее суточный цикл, и «каждый ответ новым дополнением, обрабатываем их по-очереди». |
| R6 | При недоступности OpenAI бот уведомляет чат и продолжает рассчитывать и присылать сигналы по действующему JSON, если котировки и Telegram доступны. После восстановления OpenAI автоматически обрабатывает накопившиеся за время сбоя комментарии. | Прямое требование после создания API-ключа; подтверждено продолжение сигналов по действующим правилам при сбое OpenAI и автоматическая обработка накопленных комментариев после восстановления. |
| R7 | Серверный бот рассчитывает текущие сигналы. Отдельный локальный бэктест оценивает переданный JSON на архивных тиках и выпускает PDF; общий движок используется обоими приложениями. | Прямое уточнение пользователя. |
| R8 | Факты и добавленные разработчиком допущения не смешиваются. Неизвестные правила не додумываются незаметно. | Уточнения об отделении реальных данных от собственных ограничений. |
| R9 | Экономно расходовать токены API: не раздувать промпты, передавать только необходимый для разбора комментария контекст. | Прямое требование пользователя о расходе лимита. |
| R10 | После отправки сигнала бот отслеживает достижение его стопа и цели по котировкам и сообщает результат в чат. При обновлении правил опубликованные setup/active сохраняют исходные вход, стоп, структурную цель и тейк; пересчитываются только wait_confirm/wait_entry. | Отслеживание подтверждено пользователем; сохранение уровней задано policies.positions.rule_update рабочего JSON. |
| R11 | При потере котировок бот уведомляет чат и приостанавливает новые сигналы до восстановления данных. | Пользователь подтвердил поведение при потере котировок. |

Бот выдаёт сигналы EUR/USD, GBP/USD и USD/JPY и отслеживает их по котировкам. Он не отправляет
реальные ордера брокеру. «Вход», «стоп» и «тейк» в сообщениях означают наблюдаемые
события сигнала, а не подтверждение исполнения на брокерском счёте.

Согласованы технические решения: SQLite, Telegram long polling, последовательная
очередь обработки изменений, повторы запросов и хранение времени в UTC.
Также согласовано: до лимитного входа достижение стопа/цели проверяется
по Bid для покупки и Ask для продажи.

## Торговые правила

Значения и идентификаторы реализованных политик читаются из JSON; таблица показывает их назначение.
Числа ниже описывают текущую редакцию, а не независимые константы программы.

| Предмет | Правило и источник в JSON |
|---|---|
| Инструменты | `instruments`: EURUSD, GBPUSD, USDJPY. Общая стратегия, отдельные свечи, планы, сигналы и шаг цены для каждой пары. |
| Свечи | `candles`: закрытые Bid-свечи, America/New_York с DST; H4 01/05/09/13/17/21, D1 17:00, W с воскресенья 17:00. Время событий хранится в UTC. |
| Предыдущие свечи | `context`: до W=160, D=400, H4=400; минимумы W=6, D=30, H4=30. Используются для расчёта зон, фракталов и направления каждой пары. |
| Доступное время | `policies.trade_window`: все доступные торговые часы, без фильтра сессии. |
| Зоны и направление | `policies.zones` и `policies.fractals`: FVG, гэпы, реакции, инверсии, фракталы и состояния тренда. Гэп образуется разрывом close/open и далее используется как FVG. |
| ATR и рабочая зона | `parameters` и `policies.zones`: период ATR, минимальные размеры зон, выбор ATR и зоны. Рабочая зона — с самой свежей свечи образования; при равенстве — ближайшая к цене. |
| Планы | `policies.plans`: W задаёт направление, D — планы, H4 — подтверждение, вход и сопровождение. Без недельного тренда дневные планы не строятся. |
| POI | Четыре дневных правила correction/continuation используют вызвавшую правило дневную зону. `W_point_A` использует недельную зону. |
| Цели | `policies.targets`: ближайший подходящий неснятый фрактал или FVG, для FVG — ближняя граница. D POI → D; W POI → W либо более близкая D-цель с RR не ниже `rr_min`. Фиксированная цель без структуры запрещена. |
| Стоп | `policies.plans.stop`, `parameters.stop_fallback_h4_bars`: последний подтверждённый H4-фрактал с защитной стороны зоны; при отсутствии — экстремум последних 10 H4. Буфер задаётся `stop_buffer_atr`, ATR — последней закрытой H4. |
| Вход | `policies.execution`: первая доступная котировка после подтверждающей H4; при RR ≥ `rr_min` — рыночный, иначе лимитный по политике `solve_rr_min_keep_stop_target` с сохранением стопа и цели. |
| Потолок RR | `rr_max_correction` для коррекции, `rr_max_trend` для trend/continuation. Сейчас оба равны 10, `rr_min` равен 2; значения настраиваемые. `policies.targets.mode=structural_only`. |
| IFVG | `ifvg_entry`, `ifvg_max_zone_age`, `ifvg_limit_range` задают включение входа, окно образования встречной зоны и допустимый диапазон лимитной цены. |
| Стороны цены | `policies.execution.quote_sides`: long входит по Ask, выходит по Bid; short входит по Bid, выходит по Ask. Отмена до входа по стопу/цели проверяется по стороне выхода. |
| Отмена и срок | `policies.execution.pending_cancel_on` и условия отмены; `plan_days` действует на `plan_days_statuses`. Отменённый вход позже не активируется. |
| Порядок событий | `policies.execution.event_order`: только наблюдаемые котировки. Неизвестный путь цены внутри свечи или пропуска не додумывается. |
| Параллельные планы | `policies.positions`: независимые сетапы ведутся отдельно, повтор одного сетапа не создаёт дубль. Смена плана не прекращает сопровождение его активного сигнала. |
| Суммарный риск | `max_open_risk_r=null` означает отсутствие лимита. Для заданного лимита JSON определяет `risk_per_trade_r`, `risk_counted_statuses`, `risk_queue_order`; поддержка этого варианта отмечается в плане. |
| Изменение правил | `policies.positions.rule_update`: пересчитываются `wait_confirm` и `wait_entry`; `setup` и `active` сохраняют исходные уровни до стопа, тейка или отмены. Завершённые результаты не переписываются. |
| Отключённые возможности | `policies.modules.range_trading`, `daily_point_a`, `weak_correction` выключены. Их наличие в JSON не означает отдельной задачи включить их. |

Загрузка предыдущих свечей не создаёт прошлые планы, входы и сообщения.
Отдельного переключателя исторического прогона в конфигурации нет.

## Работа с данными

Бот рассчитывает текущую ситуацию по предыдущим закрытым свечам каждой пары
и поступающим котировкам. После перезапуска восстанавливает сохранённое состояние.
Источники — подготовленные минуты HistData и текущий поток Biquote. Происхождение,
часовой пояс, единицы и пропуски сохраняются; неоднозначные интервалы не исправляются
предположениями. Исходные архивы отделены от производных файлов.

Достаточность свечей проверяется по JSON. Недостаток данных для нового сигнала
не отменяет сопровождение уже выданного по наблюдаемым котировкам. Стык источников
и недостающий период требуют проверки; равенство цен HistData/Biquote и ICE
в TradingView не установлено. Статус импорта и подключения находится в плане.

## Хранение правил и настройка

Рабочий JSON — единственный источник правил, в SQLite нет их копий или наборов
правок для восстановления файла. При запуске файл читается и проверяется;
ошибка не заменяется сохранённой конфигурацией. Telegram-правки сначала атомарно
сохраняются в JSON, затем применяются. Список инструментов применяется после
перезапуска. Состояние и контроль доступности котировок отдельны для каждой пары.

Поддерживаемые параметры и политики изменяются через JSON. Текстовые определения
не являются исполняемой программой: новый алгоритм может потребовать изменения
Rust-кода. Неподдерживаемое изменение должно быть явно отклонено с пояснением,
а не незаметно заменено другим правилом.

SQLite изменяется в существующем файле с сохранением данных и привязок сигналов.
Токены Telegram/OpenAI, модель, группа и параметры запуска хранятся отдельно
от стратегии. Все участники настроенной группы имеют одинаковые права на правки.

## Служебные сообщения и границы продукта

После успешного запуска демона в группу отправляется «Бот запущен» с временем UTC.
Это служебное сообщение; ответ на него не запускает изменение стратегии.

В stdout/journald каждые 5 минут выводятся «Работаю», время последней принятой
котировки UTC или «нет», число ожидающих планов. После обработки полной закрытой
H4 выводится результат поиска сигнала и краткая причина его отсутствия.
Эти логи не отправляются в Telegram.

Бот устанавливается пользователем вручную на Linux x86_64 под systemd.
SSH и автоматическая установка не входят в работу приложения. Пауза/откат по
команде, голосовые сообщения, отдельный внешний мониторинг, напоминания о ключах,
бюджетный контроллер, суточные сводки и подбор параметров не входят в согласованный объём.

## Локальный бэктест

`forex-backtest` запускается только локально через Docker: --strategy, обязательные
--from/--to (UTC, [from,to)), необязательные --symbols (иначе все из JSON), --output.
--data-config задаёт пути HistData отдельно от стратегии. Каталог результата новый.
Ключи, сеть и серверная БД не требуются; серверный JSON автоматически не синхронизируется.
До начала загружаются закрытые свечи и наблюдаемая часть текущих свечей; позиции
и планы начинают пустыми. minimum_bars обязателен, нехватка bars_analyzed раскрывается.
Результат по наблюдаемым тикам: рынок по Bid/Ask, лимит и тейк по уровню без улучшения,
стоп по первой наблюдаемой стороне выхода. R фиксируется расстоянием вход–стоп.
Только спред, без комиссии, свопа, дополнительного проскальзывания и задержки.
Известные исключённые интервалы помечают затронутые сделки; сценарные диапазоны не строятся.
Открытые сделки в конце показываются отдельно с текущим R и временем цены.
PDF на русском: сводка, кривая закрытого R/просадка, пары/месяцы, качество,
открытые/отменённые сигналы, 3 лучших/3 худших/3 случайных примера без повторов.
Сохраняются JSON правил и результатов, журнал JSONL, CSV сделок, графические данные,
хеши источников и версия. PDF пересобирается без прогона. Подбор параметров и
сравнение запусков не входят. Источники и рабочие базы не изменяются.

### Визуальный стандарт PDF

Оформление отчёта за октябрь 2026 года одобрено пользователем 10.11.2026
и принято за стандарт последующих отчётов. Светлый A4, тёмно-синяя шапка,
крупные карточки показателей, компактные таблицы и крупные свечные графики.
Убытки и ограничения данных остаются заметными: красные акценты результата,
отдельные плашки пропусков. Цвет дополняет числовые значения и подписи.
Сводка предшествует деталям и качеству данных; каждый пример сделки начинается
с новой страницы. Количество страниц зависит от данных, а не фиксируется шестью.
Точные параметры и композиция закреплены в
[архитектуре](architecture.md#визуальное-оформление-pdf).

### Комплект обновления серверного бота

По уточнению пользователя deploy предназначен только для обновления: бинарник,
новый рабочий JSON, инструкция и SHA256SUMS. Базы, секреты и unit исключены.
Весь каталог deploy исключён из публичного репозитория, включая инструкцию
конкретной установки и контрольные суммы. Доставка через SFTP в выбранный
владельцем сервера каталог; существующая служба сохраняет свои пути запуска.
После установки бинарника и JSON существующая серверная БД пересчитывается
командой prepare-state без резервной копии (прямое указание пользователя).
Стратегия, включая одновременные сетапы, в рамках упаковки не меняется.

### Пара в сообщении сигнала

Сообщение указывает инструмент сигнала. Подстановка EURUSD при отсутствии
или некорректном формате пары запрещена. Если определить пару нельзя,
формирование сообщения возвращает явную ошибку; торговое сообщение не создаётся.

## Контракт стратегии v2

Файл является строгим JSON с явными числами и типизированными политиками.
Поля comment поясняют настройки, но не влияют на расчёты. OpenAI получает их
и может редактировать по просьбе пользователя; неподдерживаемые условия нельзя
реализовать одной правкой пояснения. Изменение только comment/messages не
пересчитывает планы. Формат v1 больше не читается, конвертера нет.

Пять ранее текстовых окон заданы положительными целыми параметрами в барах:
запасной H4-стоп, возраст встречной зоны подтверждения H4, окно недельного
снятия и отдельные D/W-окна фрактальных целей. Смысл и единицы всех полей,
соответствие v1/v2 и ограничения описаны в [архитектуре](architecture.md).
Нереализованные weak_bars и отметка дневного снятия за 30 баров удалены;
отключённые модули остаются явно отключёнными, новая торговая логика не добавлена.
