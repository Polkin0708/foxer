# План разработки и проверок

Торговая точка истины — локальный `strategy/fvg-bot-rules.json`, торговая редакция
`agreed-v4`, формат v2. [Требования](requirements.md) задают продукт, [архитектура](architecture.md)
— устройство. Этот документ содержит порядок работ, критерии приёмки и датированные
результаты. Старые проверки не подтверждают более поздние изменения JSON или кода.

## Текущее состояние

На 12.11.2026 код использует единую индексную цену Upscale, чистую SQLite v4
(data/signals.sqlite) и индексный формат локальной истории. Загрузчика истории
нет; живой бот накапливает свечи сам. Ниже сохранены датированные результаты
предыдущих этапов; они не являются инструкциями миграции новой версии.

### Предыдущий этап, 10.11.2026

На 10.11.2026 в проекте есть Rust-приложение: импорт архивных котировок, агрегация свечей,
SQLite, расчёт планов и сигналов, Telegram/OpenAI, прежний поток котировок, очередь
комментариев, восстановление состояния и поставка под systemd.
Адаптация к `agreed-v4` завершена и проверена локально 10.11.2026:
129 Rust-тестов, rustfmt, Clippy, миграция копии реальной SQLite и автономная
Linux x86_64-проверка прошли. Установка на сервере и живые интеграции отдельно.

Рабочий JSON задаёт сетку America/New_York с DST, параметризованные RR и
сохранение уровней `setup`/`active`. Старые механизмы фиксированной сетки,
фиксированных политик RR и переключения опубликованных уровней не являются
требованиями к новой версии.

Известные ограничения текущего контракта:

- Переключатель исторического прогона удалён из контракта и JSON.
  При загрузке состояния серверного бота предыдущие свечи нужны для текущего
  расчёта; отдельное локальное приложение выполняет исторический торговый прогон.
- `max_open_risk_r` пока допускается только `null`. JSON описывает также вариант
  с лимитом и очередью риска; он не должен считаться реализованным и не включается
  молча. Это ограничение кода, а не запрет стратегии на такой вариант.
- Выключенные модули и структурный режим целей не означают готовности других значений.
  Изменение неподдерживаемой политики требует явной проверки и, при необходимости,
  реализации. Текстовые условия не исполняются как программа.
- `describe-config` v2 описывает поля, ограничения и доступность Telegram-правок;
  признак engine_implemented=true не означает реализации отключённых модулей.

## Порядок работ

Для каждого изменения поведения: сначала документация по JSON, затем тест,
который воспроизводит отсутствие поведения или ошибку, запуск до реализации
с фиксацией причины падения, минимальная реализация и повторные проверки.
Все Rust-проверки и сборки выполняются в Docker с зафиксированными зависимостями.
Обычные тесты используют искусственные данные, управляемое время и подменяемые
сервисы; не требуют ключей, живого рынка или платных вызовов.

### 1. Контракт JSON

Проверить загрузку текущего файла, поля, перечисления, ссылки, диапазоны,
неизвестные/повторные ключи и ID правил. Карта блоков должна ссылаться на реальные
пути текущего JSON. Перестановка правил не должна менять их смысл.
Значения RR, ATR, сроки и шаги цены читаются из JSON без противоречащих копий.
Неподдерживаемое значение отклоняется явно, файл не заменяется данными из SQLite.

**Приёмка:** `check-config` и `describe-config` для текущего JSON, негативные
проверки контракта и согласованности ссылок. Относится к R2, R8.

### 2. Свечи, источники и состояние

Привести импорт и текущий поток к общей сетке `candles`; сохранить источник,
единицы, UTC-время и признаки пропусков. Проверить изоляцию инструментов,
достаточность свечей и восстановление после перезапуска. Правила хранятся только
в JSON; SQLite содержит состояние и хеш, но не копии правил.

**Приёмка:** границы H4/D/W зимой, летом и при DST; котировка ровно на границе;
неполные и незакрытые бары; отсутствие выдуманных минут; повтор события и импорта;
конфликт данных; сохранность состояния и комментариев после перезапуска.
Загрузка предыдущих свечей рассчитывает зоны и направление без прошлых сигналов.
Сопровождение выданного сигнала не прекращается из-за нехватки свечей для нового.
Относится к R2, R7, R8, R11.

### 3. Торговая логика

Проверить реализацию блоков `policies.zones`, `policies.plans`, `policies.targets`,
`policies.execution` и `policies.positions` по текущему JSON. Не добавлять торговых ограничений из прежних
описаний или исследовательских скриптов.

### 4. Telegram и изменение правил

Сохранить приём ответов всех участников группы, текстов и изображений,
последовательный OpenAI-разбор и надёжную запись JSON. После правки пересчитывать
только `wait_confirm`/`wait_entry`; уровни `setup`/`active` сохранять по
`policies.positions.rule_update`.

**Приёмка:** ответы разных авторов по очереди, изображения и уточнения,
невалидный ответ API, недоступность OpenAI с последующей обработкой очереди,
продолжение сигналов при сбое API, ошибка записи JSON, сбой до/после rename,
повтор update и перезапуск. Проверить неизменность входа/стопа/цели/тейка
`setup`/`active` после правки и неизменность завершённых результатов.
Проверить привязки сообщений и доставку после сбоя без повторного применения
правил. В API передаётся только необходимый контекст, расход сохраняется.
Относится к R3–R6, R8–R10.

### 5. Чистая БД и локальная поставка

Проверить создание чистой SQLite v4 по пути data/signals.sqlite и восстановление
нового состояния после перезапуска. Старые БД и архивы не переносить,
не изменять и не подключать; миграция не требуется.

После целевых тестов выполнить полный Rust-набор, rustfmt check и Clippy
с `-D warnings` в Docker, собрать Linux x86_64 и выполнить автономный smoke-test
на новой тестовой БД. Проверить содержимое поставки; не подменять рабочие БД и секреты.
Сообщение запуска и два диагностических лога проверяются автономно.

**Приёмка:** зафиксированные результаты проверок и контрольная сумма нового
бинарника. Это подтверждает локальную поставку, не установку на сервере.
Относится к R1, R4, R6, R8, R10.

### 6. Живые подключения и сквозная приёмка

Отдельно проверить историю индекса Upscale и её стык с текущими снимками,
разрывы и переподключение. Пройти путь сигнал → комментарий со скриншотом →
изменение JSON → пересчёт ожидающего плана при сохранении уже выданных уровней →
наблюдаемый результат сигнала. Проверить уведомления о сбоях и восстановление.
При необходимости использовать явно обозначенный тестовый сигнал.

Установка на сервер выполняется пользователем вручную; после неё отдельно
проверяются systemd, автозапуск после перезагрузки и journald. SSH не используется.

**Приёмка:** подтверждены R1–R11 в соответствующем окружении. Прибыльность,
бэктест и подбор параметров не являются критериями корректности.

## Проверки реализации agreed-v4, 10.11.2026

Контракт, календарь, расчёты и восстановление адаптированы. До изменения
реализации тесты подтвердили отказ нового JSON на timezone, старую летнюю
